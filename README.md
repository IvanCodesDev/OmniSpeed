## OmniSpeed 是什么

与只能作用于单个浏览器的倍速插件不同，OmniSpeed 是一款常驻系统托盘的**桌面应用**：一套全局快捷键同时控制 Chrome / Edge / Firefox 里的网页视频和 VLC / PotPlayer / mpv 等本地播放器，倍速范围 0.25×–16×，并对哔哩哔哩、抖音、YouTube 等主流平台做了防复位适配。完全本地运行、零数据外传、开源可审计。

## 为什么不用浏览器插件

| | 浏览器倍速插件 | OmniSpeed |
| --- | --- | --- |
| 生效范围 | 装了插件的那一个浏览器 | 浏览器 + 桌面播放器，全局统一 |
| 换个软件 | 失效，得重新找方案 | 同一套快捷键继续用 |
| 倍速上限 | 受站点 UI 限制，通常 2×／3× | 直接控制播放内核，最高 16× |
| 切集／拖进度 | 常被站点脚本复位回 1× | 倍速锁定，持续保持目标倍速 |
| 多软件切换 | 各记各的 | 按应用／网站记忆，切回自动恢复 |

## 功能

- **全局快捷键**：任意软件在前台时，`Ctrl+Alt+↑/↓` 都能调速，屏幕悬浮提示当前倍速。
- **突破平台上限**：平台菜单最高 2×／3× 只是 UI 限制，OmniSpeed 直接控制浏览器播放内核，可用 0.25×–16× 的任意倍速。
- **倍速锁定**：拦截站点在切集、切 P、拖进度、自动连播时对倍速的复位；你在播放器上主动调速则会被尊重并同步。
- **短视频流跟随**：抖音、快手、YouTube Shorts 滑到下一条时自动继承当前倍速。
- **桌面播放器适配**：mpv、VLC、PotPlayer 优先走控制接口，一步设到精确倍速、无需窗口在前台；其余播放器用模拟快捷键兜底。
- **平台客户端接管**：哔哩哔哩桌面端等 Chromium 套壳客户端一键接管后，经仅本机可见的 CDP 通道直接控制内部视频——客户端里也能 0.25×–16× 任意倍速，突破其自带 2×/3× 档位。
- **按应用记忆**：记住每个应用／网站上次用的倍速，切回去自动恢复。
- **直播与广告识别**：直播流禁用倍速并提示，平台广告时段不干预，正片恢复。
- **本地优先**：不联网、不采集浏览内容，所需系统权限均可在设置中关闭。

## 能力边界

有些事从软件外部做不到，这里说明白，避免误解：

- **无法让任意封闭软件的画面加速**。视频的解码与渲染发生在目标软件进程内部，外部无权干预。OmniSpeed 的做法是"统一遥控器"——对浏览器精确设速，对播放器走控制接口或模拟它自己的快捷键，而不是劫持任意像素。
- **超过约 4× 后浏览器会静音**。这是浏览器内核的预期行为（不再做音频时间拉伸），OmniSpeed 会明确提示并提供一键回到 4×。
- **高倍速吃带宽**。5× 播放需要约 5× 的实时带宽，弱网下可能追着缓冲卡顿，可开启智能降速自动回落。
- **不绕过任何付费、DRM 与防作弊校验**。部分网课平台会校验播放进度，高倍速可能不被平台承认。

## 从源码构建

前置要求：

- Node.js ≥ 20（含 npm）
- Rust stable 工具链
- Windows：WebView2 运行时（Windows 11 自带）

在仓库根目录执行：

```bash
npm install          # 安装依赖（npm workspaces）
npm run dev          # 仅前端：Vite 开发服务器，浏览器预览界面
npm run tauri dev    # 桌面应用：编译 Rust 并启动窗口
npm run tauri build  # 打包 NSIS 安装包（按当前用户安装，免管理员）
```

打包与发布说明：

- 安装包启用了自动更新产物（`createUpdaterArtifacts`），构建前需配置更新签名私钥：
  `tauri signer generate -w <路径> --password <密码>` 生成密钥对，公钥写入
  `tauri.conf.json`（已配置）；构建时设置环境变量 `TAURI_SIGNING_PRIVATE_KEY`
  （私钥文件内容）与 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`。私钥请勿入库。
- 自动更新清单指向 GitHub Releases（`latest.json`），发布时把 `tauri build` 产出的
  安装包与 `*.sig`、`latest.json` 一并上传到 Release。
- 正式分发需要 Windows 代码签名（Authenticode）：全局键盘钩子 + 模拟输入易被杀软
  误报（开发文档 §7.6），拿到证书后在 `bundle.windows.signCommand` 接入签名命令。

### 八站网页端真机回归

站点适配规则此前都是照文档写的「最佳努力值」，从未在真实页面上验证过。M4.7 用
Chrome + 解包扩展 + CDP 自动化把八站逐个跑了一遍：每站导航真实播放页，检查倍速锁定脚本
是否注入、适配器与播放器选择器是否命中、直播/广告识别是否正确，并完整走一遍
「2.5× → 站点复位被拦截 → 16× 突破站点上限 → 恢复 1×」。

| 站点 | 结果 |
| --- | --- |
| 哔哩哔哩 / 抖音 / YouTube / 腾讯视频 / 爱奇艺 / 优酷 / 快手 | 全链路通过 |
| 西瓜视频 | 网页端已被站点关闭（`www.ixigua.com` 强制跳转 App 下载页），规则保留待站点恢复 |

回归揪出并修掉了两个真实缺陷：

- **优酷全站倍速失效**：广告层容器被播放器常驻在页面里（无广告时是看不见的空壳），
  旧判据把它当成「正在放广告」，而广告时段本就会暂停倍速干预 —— 于是优酷上倍速跟随、
  防复位、导航恢复全部悄悄失效。现改为只有广告层里真的画出了内容才算广告时段。
- **腾讯视频播放器定位失准**：规则里的容器类名比实际少一个字母，从未命中过，
  一直靠通用兜底掩盖；同屏多个播放器时会选错主视频。已按真机结构校准。

回归与校准工具在 `apps/extension/test/`，用法见[扩展 README](apps/extension/README.md#测试)。

### 百度网盘桌面端：让模拟按键也能精确设速

百度网盘的播放器界面是 Electron，画面却由原生播放器解码后合成上去，页面里**没有
`<video>` 元素**。控制接口与 CDP 那套（都建立在 `playbackRate` 上）对它一律无效，
能用的只剩播放器自带的键盘快捷键。

模拟按键此前只能「按一下快一点」，因为相对步进离不开当前倍速，而按键通道读不回来。
百度网盘的数字键 `1`–`5` 给的却是**绝对倍速**——按下即钉死到确定值。有了这种绝对档位，
先按最近的档位键、再用 `,` / `.` 补足差额，全程不需要知道播放器的原状态，
于是模拟按键第一次做到了精确设速：**0.5×–5×，0.1× 精度，最多 6 次按键**。

一个只有真机才暴露的坑：步进键要先读回当前倍速再加减，而播放器把这一步摊在异步 IPC 上。
连发太快时后一次读到的还是旧值，两次按键算出同一个结果，**表现为静默少走一格**——
按键通道没有回读，少走的这一格永远补不回来。因此连发间隔是各播放器的实测值
（百度网盘 150ms），跨档位设速时能看见倍速爬升半秒左右，属正常。

模拟按键需要播放器窗口在前台，OmniSpeed 会在下发前自动激活它。

### 模拟按键：下发前先中和用户按着的修饰键

全局快捷键按定义就带修饰键（默认 `Ctrl+Alt+↑/↓/0`），触发的那一刻用户十有八九还按着
`Ctrl` 和 `Alt`。此时发给播放器的 `.` 会被系统合成成 `Ctrl+Alt+.`——播放器不认这个组合，
整条丢弃。真机上的表现是**悬浮提示跳到了目标值、画面倍速却纹丝不动**，
而且所有走模拟按键的播放器都中招，只是此前的验证都绕开了快捷键这条路才一直没暴露。

现在下发前会先把用户物理按着的修饰键抬起来，发完原样按回去，整串一次性提交，
中间不存在「修饰键半开」的时间窗。按回去这一步不能省：按住 `Ctrl+Alt` 连点 `↑`
是常规用法，修饰键若停在抬起状态，从第二下起快捷键就不再匹配。
另外单独抬起 `Alt`／`Win` 会被系统读成呼出窗口菜单／开始菜单，抬起顺序把 `Ctrl` 垫在最后，
用户没按 `Ctrl` 时则临时补一个把这个动作遮掉。
